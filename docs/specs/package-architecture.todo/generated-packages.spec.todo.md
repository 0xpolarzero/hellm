# Generated Packages Spec Todo

## Status

- Status: future generated package spec todo
- Scope: generated local packages consumed by agents and Smithers workflow source

## Purpose

Generated packages provide stable, intuitive imports for agent-authored TypeScript and Smithers
workflow source.

They are generated local packages, not public reusable SDK packages.

## Package Names

The target generated package names are:

```text
@svvyx/workflows
@svvyx/extensions
```

`@svvyx/*` means "svvy-generated extension/workflow context available inside agent and workflow
runtimes."

## `@svvyx/workflows`

`@svvyx/workflows` is generated by the Workflows builtin extension.

It exports reusable workflow assets:

```ts
import { Agents, Components, Prompts, Workflows } from "@svvyx/workflows";
```

The root public shape is:

```ts
export * as Agents from "./agents";
export * as Components from "./components";
export * as Prompts from "./prompts";
export * as Workflows from "./workflows";
```

Rules:

- It is generated from app-global reusable workflow source.
- It is read-only to ordinary agent edits.
- It is linked into workspace `.smithers/node_modules`.
- It is visible through the Workflows generated-surface pane.
- It is taught by Workflows extension guidance, not by Smithers extension guidance.
- It may import Smithers workflow-authoring dependencies required by the generated workflow source.
- It may import `@svvyx/extensions` when generated task-agent source needs extension reference
  values.
- It must not import public `@svvy/extensions`.
- Its `Prompts` namespace contains reusable workflow prompt assets saved through the Workflows
  source library. It is not a public `@svvy/prompts` package and is not the location for default
  actor prompts or extension instructions.

## `@svvyx/extensions`

`@svvyx/extensions` is generated by the Workflows builtin extension from the current extension
reference set.

It exposes extension reference values for workflow task-agent parameter records:

```ts
import { Extensions } from "@svvyx/extensions";
```

Rules:

- It is generated output.
- It is read-only to ordinary agent edits.
- It is linked into workspace `.smithers/node_modules` when workflow source needs extension
  references.
- It is not the same thing as the public `@svvy/extensions` package.
- It is not the same thing as the actor-scoped `extensions` object inside `execute_typescript`.
- It is self-contained unless an explicit type-only import from `@svvy/core` is required.
- It must not import public `@svvy/extensions`.

## `execute_typescript` Runtime Object

Inside `execute_typescript`, loaded extension clients remain an injected runtime object:

```ts
extensions.artifacts.run("inspect", { args: { artifactId } });
extensions.workflows.run("list", { options: { json: true } });
```

That object:

- contains only loaded callable TypeScript clients for the current actor
- is not imported from a package
- is governed by `@svvy/extensions`
- creates child command facts under the parent `execute_typescript` command

## Migration From Current Names

The current generated package names are:

```text
@svvy/workflows
@svvy/extensions
```

The target design replaces them with:

```text
@svvyx/workflows
@svvyx/extensions
```

The migration must update:

- generated package manifests
- generated source imports
- workspace `.smithers/node_modules` links
- stale workspace `.smithers/node_modules/@svvy/workflows` and generated
  `.smithers/node_modules/@svvy/extensions` links
- Workflows extension instructions
- any existing Smithers spec/generator text that currently teaches reusable Workflows imports,
  moving that text into Workflows extension guidance
- `execute_typescript` import allowlist and generated declarations
- Workflows pane labels and read models
- tests and fixtures

The migration must remove the old generated names instead of keeping compatibility aliases.

## Dependency Rules

- Generated packages are outputs of `@svvy/extensions`.
- Generated packages must not import `@svvy/runtime`, `@svvy/desktop`, public `@svvy/extensions`,
  or source-checkout-relative modules.
- `@svvyx/extensions` should be self-contained; if implementation needs shared nominal ids, it may
  use type-only imports from `@svvy/core`.
- `@svvyx/workflows` may import Smithers workflow-authoring dependencies required by generated
  workflow source and may import `@svvyx/extensions`.
- Generated packages must resolve from workspace-local links or generated package paths, not ambient
  global package resolution.
- Generated packages must not depend on the desktop app bundle, a source checkout, or repo-root
  authoring assets.
